How reliable is tomorrow's wind forecast?

GB wind · January 2026 pilot

Part 1 · Pilot walkthroughPart 2 · Technical review
This pilot checks how reliable the available wind forecast was before buying power. We replay January 2026 using only forecasts published by the chosen cutoff, then show how the app is built.

Buy before delivery. Use only what was known.

1 · The decision
Forecasts update throughout the day; the relevant deadline depends on the auction. Morning energy gates close at 09:20 and 09:50 GMT, while EPEX's half-hourly auction closes at 15:30 GMT. The demo's 10:00 cutoff is after the morning gates but before the afternoon gate. Use a cutoff before the auction you intend to trade.

There is more than one day-ahead auction. EPEX's hourly energy auction closes at 09:20 GMT, with results from 09:30. N2EX closes at 09:50 GMT, with results by 10:00. EPEX's half-hourly energy auction closes at 15:30 GMT, or 3:30 pm, with results from 15:45. Half-hourly describes delivery contracts, not the length of the auction. Nemo Link sells interconnector capacity, not energy; its 09:00–09:30 CET window is 08:00–08:30 GMT in January. Match the app's cutoff to the product and check the operator's calendar outside this January example.

Technical review

Architecture · Data · Method · Tests

Part 2 · Technical review
Now switch from the findings to how the app works: request routing, React rendering and API calls, the data snapshot and caches, then code and checks.

Two services. One data snapshot.

Architecture
The browser loads the Next.js interface, then requests JSON from the same site's /api paths. On Vercel, routing sends /api directly to FastAPI, not through a Next.js API handler. Locally, a Next.js rewrite proxies to BACKEND_URL. FastAPI reads the bundled snapshot; there is no database or request-time download.

Server shell. Client-side data.

Rendering & API

React rendering

Server Components: layout and route wrappers.

Client Components: dashboard state, controls and charts.

Suspense: boundary for useSearchParams(), not API loading.

No server-side forecast fetch or Server Actions.

Browser request flow

URL date / cutoff → useEffect → fetch → JSON → React state.

/api/forecast?delivery_date=2026-01-16&cutoff=10:00
/api/monthly?cutoff=10:00

15-second timeout · abort superseded requests · retry on error.

Previous result stays visible while the next loads.

Same-origin requests: Vercel routes to FastAPI in production; Next.js proxies locally.

Yes, the layout and page wrappers are React Server Components, but they do not fetch forecast data. Interactive dashboards are Client Components. Suspense supports their useSearchParams hook; loading and errors for API calls use explicit state. Changing date or cutoff updates the URL and triggers browser fetch. Requests time out after 15 seconds and abort on cleanup; previous results stay visible. Retry makes a new request. No SWR, React Query, or Server Actions are used.

Caches are disposable: cold starts / new workers rebuild them. Refresh the snapshot and redeploy to update data.

FastAPI validates inputs before calling analysis.py. The first analysis request loads compressed files into dictionaries indexed by publication and target time, and by actual half-hour. Python LRU caches reuse the loaded data and calculated responses: 64 daily keys, 32 monthly keys, and one all-cutoff comparison. These caches belong to each Python process, not the whole deployment; a cold start rebuilds them. The committed snapshot is the source of truth. Updating data means rerunning the downloader and shipping a new build, not writing to a live database.
